# Contributing

Thank you for helping improve the AI Security Testing Framework.

## Contribution principles

- Preserve the framework's existing assurance areas, lifecycle model, and modular approach unless a change is explicitly proposed and justified.
- Prefer reproducible evidence over unsupported capability or performance claims.
- Keep model-specific limitations and threat-model assumptions visible.
- Do not describe a test as executed unless the underlying method ran successfully.
- Use official tool documentation and APIs; record versions and compatibility constraints.
- Keep secrets, personal data, customer content, and proprietary model artefacts out of public commits.

## Suggested workflow

1. Open an issue describing the problem, proposed change, and affected framework area.
2. Keep changes focused and avoid unrelated restructuring.
3. Update relevant documentation, applicability notes, and templates.
4. For code or notebooks, include dependency versions, a reproducible run path, and expected outputs.
5. Record failed or skipped test cases honestly.
6. Submit a pull request with a concise summary, validation performed, limitations, and evidence.

## Documentation style

Use consistent terms: assessment area, testing module, test status, observation, potential finding, and confirmed finding. Define acronyms on first use. Distinguish framework guidance from implemented tooling and measured results.

## Security-sensitive contributions

Do not submit live credentials, private keys, production data, exploitable customer details, or unredacted vulnerability evidence. Follow SECURITY.md for responsible reporting.
